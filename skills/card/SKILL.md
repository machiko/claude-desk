# /desk:card

腳本是 `python3 ${CLAUDE_PLUGIN_ROOT}/skills/card/scripts/card.py`（下面寫成 `card.py`）。收到 `/desk:card <args>` 時：

- `new`、`archive`、`changelog` 與 `overlap`：直接執行 `card.py <args>`，把輸出原樣給使用者。
  - `overlap <目標>`：唯讀，列出這張卡的實作計畫跟登錄表上其他進行中的卡（已歸檔段、卡片檔不存在、沒填計畫的不算）同檔的檔案，每個同檔一行「同檔預警：<檔> 也在「<卡名>」的實作計畫（<slug>）」，沒有印「同檔預警：無」。有同檔時建議「先合哪張」或「改成疊放（`new` 時 base 指向另一張的分支）」，不要自己改 base 或順序。
  - `new` 帶 `--trivial`（放哪個位置都行，可以同時給 base）開「瑣事卡」：只改註解、CHANGELOG、沒被測試引用的說明文字時用。腳本在「## 規格」第一行寫「類型：瑣事（…）」、關卡直接設 `spec：待確認規格（瑣事）`，驗收情境維持範本（面板跟一般卡一樣提示去寫規格）；規格怎麼寫見下面「產生規格」的瑣事卡段。
  - `new` 之後提醒：接著用 `/desk:card spec <slug>` 產生規格。`new` 不建 `changelog.d/<slug>.md`（空片段會讓發版合併報錯），條目由實作時寫。橫切重構（改名、搬檔、改六段結構）的卡要等其他卡合併、或其他卡等它合併，見 `docs/WORKFLOW.md` 的「開卡順序」。
  - `archive` 之後**不要**替使用者刪 worktree 或分支；只印出指令由使用者自己跑。例外：發版時，`/desk:release` 請求括號裡列的、請求帶面板確認段或使用者在 `/desk:release` 的確認題選了照做的那幾張卡，照那份 skill 的時機跑 `card.py archive <slug>… --cleanup`（一次給多張；有一張找不到就整批不做）。它只用 `git worktree remove`、`git branch -d`（唯一例外：worktree 含 submodule 時 git 不加 `--force` 一律拒絕，腳本在自己確認乾淨後（每個 submodule 內部也要沒有未提交改動、沒有被忽略的本機設定、沒有 stash、所有 ref（HEAD、本機分支、tag）與 reflog 找得到的 commit 都在它的遠端分支上（上游有不在任何分支上的 tag、或改寫過歷史時會多保留）；有 deinit 過、git 目錄還在卻沒 checkout 的 submodule 一律保留）才改加 `--force` 再試一次，輸出註明「含 submodule，以 --force 移除」），主 worktree、沒併入主 repo 目前分支、有未提交改動、有被 git 忽略的本機設定或資料（`.env*`、`*.local.*` 等）或 git 拒絕的都保留，原因與自己刪的指令寫進登錄表「## 提醒」；其他被忽略的檔會隨 worktree 一起刪，可重建的（`node_modules`、`__pycache__` 等）以外列在輸出與提醒；squash／rebase 合併的（內容已在主 repo、分支不是祖先）照樣移除乾淨的 worktree，分支因為 `branch -d` 認不出而保留、寫進提醒；輸出（每張一行「清理 <slug>：…」）原樣給使用者，保留的項目不要自己再加 `--force`／`-D` 去刪。發版請求沒列到的卡、有 `release：` 關卡的卡不帶 `--cleanup`。
    - 歸檔回顧（有 `card.retro` 時）：`card.py archive` 在複製完 `.task` 檔後、清理前會執行該指令並印出輸出。回顧輸出若有「候選 pitfalls」時，對話用 AskUserQuestion 提最多 3 條（格式「類別：怎麼避免」，可複選）；使用者勾選後才追加到 `review.pitfalls`（或專案 `review-pitfalls.md`）檔尾「## 追加」段（檔案不存在或沒有該段就建立），沒勾選就只留在 `retro.md`，不主動修改 pitfalls。
  - `changelog <版本>`：要發的 PR 都合併之後，在要發版的那份 main 執行（主 repo；照 `/desk:release` 發版時是從 origin/main 開的暫存 worktree）；它把 `changelog.d/*.md` 合併成 `## <版本>` 段並刪掉片段檔，沒有片段、版本段已存在、片段不是 `- ` 開頭都會報錯不改檔。`/desk:release` 請求帶面板確認段、或使用者在確認題選了照做時，由對話照那份 skill 列的動作做完（規則見那份 skill）；其他情況照舊由使用者自己做，不要替他 commit。
    - 專案的 dispatch.json 設 `"card": { "changelog": { "format": "keepachangelog" } }` 時改依 Keep a Changelog：`## [Unreleased]` 的手寫內容與片段一起移進 `## [<版本>] - <今天>` 段（版本照輸入保留，`v26.2.7` 就是 `[v26.2.7]`），`[Unreleased]` 留空標題；條目依動詞分進 `### Added／Changed／Removed／Fixed／Security`（新增→Added、調整→Changed、移除→Removed、修復→Fixed、修補→Security），同類手寫在前、片段在後，其他手寫小節（如工程專區）原樣排最後。片段動詞不在對照表會指出檔名與條目並報錯；版本段已存在、沒有片段且 `[Unreleased]` 是空的也報錯，都不改檔。
- `spec <目標> ok`：執行 `card.py spec-ok <目標>`（清關卡、狀態改「規格已確認…，可派實作」、記 Decisions／History），輸出原樣給使用者；輸出結尾有「同檔預警：…」行（實作計畫跟其他進行中的卡改同一個檔，已記進 History、不擋確認）時一樣原樣轉給使用者。確認後，這個回合結束時面板照 t 的規則自動派實作（只有使用者明確說要確認時才跑，subagent 跑的不派）。只有使用者明確說要確認時才跑，不要自己判斷規格夠好就替使用者確認。
- `done <目標> <狀態一句>`：執行 `card.py done <目標> <狀態一句>`，輸出原樣給使用者。在主對話（不派背景 Agent）改了檔案、commit、跑了測試或做了決策，告一段落時用：狀態改成那句（60 字內，沒驗證的寫「待確認」）；下一步依關卡三選一：驗收已過關（關卡 `review：…` 四個分級都有數字、CRITICAL 與 HIGH 都是 0）而且 `.task/REVIEW.md` 寫好之後有新 commit，寫「等自動重新測試與驗收；沒動靜就到面板按 v」；驗收已過關但之後沒有新 commit（或沒有審查檔，關卡是對話自己寫的），寫「到面板照「輪到你」開 PR 或合併」；其他寫「到面板按 v 執行測試」；History 記日期、分支、HEAD 短 sha 與那句（有未提交的檔會註明幾個）；「等你」「關卡」「檢查」不動。規格還沒確認（關卡是 `spec：…` 或認不到填好的 AC）會拒絕。狀態只寫發生了什麼：那句含 commit（7～40 碼英數混合的 hex）、`AC-數字` 或 `D-數字` 時也會拒絕、卡片不動，這些代號寫在 History。它不會把測試或驗收標成通過，那由面板 `v` 與自動流程記錄。整段流程見 `/desk:flow`。
- `spec <目標> [需求描述]`：照下面「產生規格」做。
- 沒帶參數就印用法，不猜。

`<目標>` 可以是 worktree 資料夾名（slug）、任務名（完整或唯一部分）或 `main`（主 repo）。

設定（主 repo、worktree 位置、登錄表、模板、專案規則）在 desk 的 `dispatch.json`：全域那份疊上目前專案的 `~/.claude/handoffs/<repo>/dispatch.json`，說明見 `card.py` 開頭。要在專案的 repo 或 worktree 裡執行。

## 產生規格（spec）

規格是這件事的唯一依據：審查會逐條對照驗收情境，「沒做到」「沒測到」都算 HIGH，會被自動修正。所以每一條都要寫得能驗證。

1. **找卡**：`card.py card <目標>`，記下 path、root、format（DESK 新卡／CARD 舊卡）、branch、gate、check、spec、已填的 AC、user，以及 `rule:` 開頭的專案規則（寫規格時都要遵守）與 `suggested check:`。找不到就把腳本列出的任務給使用者選，不要猜。
2. **讀現況（唯讀）**：
   - 整張卡：狀態、下一步、Scope、Decisions、History。
   - `git -C <root> log --oneline -10`、`git -C <root> status --short`；分支已有改動就看它相對 merge-base 的 `git diff --stat`。
   - 需求牽涉的程式：路由、控制器／服務、權限設定、既有測試。範圍大就派 Explore agent 查，只帶回結論。
   - 不改程式、不 commit、不碰其他任務的卡。
2b. **規格前審（有 `spec preflight:` 時）**：
   - 步驟 1 印出 `spec preflight: <指令>` 時，先決定 `--paths`（步驟 2 讀到的相關程式模組，逗號分隔路徑清單）；將 `{root}` 換成任務根目錄、`{card}` 換成卡片路徑、`{paths}` 換成模組路徑，其餘佔位原樣保留。
   - 相關檔只有 1～2 個（小卡）就不跑前審，History 記一行：`- YYYY-MM-DD HH:MM：規格前審：略過（小卡：相關檔 n 個）`。
   - 相關檔 3 個以上：用 Bash 的 `run_in_background` 在背景執行前審指令，不停下來等；同時繼續讀程式、想釐清題、擬規格草稿。步驟 5 寫進卡片前收結果：讀取輸出檔（預設 `.task/SPEC-gemini.md`），還沒跑完就等它跑完（不另設逾時）。
   - 候選清單只當建議：與卡片 Scope、非目標衝突的丟掉；採用的寫進 AC 表，並在「對應測試」欄保留建議的測試名（標（新））。
   - History 加一行：`- YYYY-MM-DD HH:MM：規格前審：候選 m、採用 n、<丟棄原因一句>`（全數採用時寫全數採用）。
   - 指令執行失敗（找不到指令、非 0、超時）就跳過前審照常寫規格，History 記一行：`- YYYY-MM-DD HH:MM：規格前審：略過（<原因>）`。
   - desk 不執行也不檢查這條指令。
2c. **瑣事卡（步驟 1 印出 `trivial: yes` 時）**：跳過 2b 規格前審與 4 釐清問題；步驟 5 照做但精簡：目標一句、非目標可省、驗收情境由這一步預填成一條（給定「改動只有文字或註解」、當「跑完成檢查與 CI」、則「全過，沒有測試斷言被改壞」、對應測試「完成檢查與 CI」，要補可補）、實作計畫照列要改的檔、History 照記；關卡維持 `spec：待確認規格（瑣事）`，不改成 AC 範圍那句。確認規格、完成檢查、CI 與審查的風險判斷都跟一般卡相同。
3. **已有規格時**：`filled AC` 不是 none，就先用 AskUserQuestion 問「取代／只補缺漏／取消」，照答案做。
4. **釐清問題**：只想「答案會改變驗收情境」的事，能從卡片或程式讀到的不算。
   - 有推薦答案的題不停下來問：照推薦寫進規格，Decisions 每題記一筆預設決定（寫法見步驟 5），使用者確認規格時一起看、要改再改。
   - 只有兩個選項都合理、沒有推薦，或選錯要重寫大半規格的題，才用 AskUserQuestion 問（一次最多 4 題；每題 2–4 個具體選項），其他題照推薦寫成預設。
   - 優先想：誰能用（角色與資料範圍）、邊界與錯誤時要怎樣、哪些明確不做、有沒有寫入操作、要不要相容舊資料。
   - 需求描述與卡片已經夠清楚就不問，直接寫。
5. **寫進卡片**：
   - `card.py spec-init <目標>`（沒有規格段才會插入模板的空白段）。
   - 用 Edit 改那張卡的「## 規格」：目標一句、非目標一句、驗收情境表 3–5 列。寫入前重讀卡片；跟步驟 2 讀到的不同就停下回報，不要覆寫。
   - 每一列：
     - 給定：角色、資料、前提狀態。
     - 當：操作或事件。
     - 則：看得到的結果（畫面、回應碼、資料、log），不寫實作方式。
     - 對應測試：既有的寫測試的完整名稱；還沒有的寫預計名稱並標（新）。
   - 牽涉權限、資料範圍或寫入時，至少一列寫越權或範圍外的情境。
   - 改到自動流程、狀態旗標或解析器時，另列「維持現狀」的情境：受影響的相鄰路徑（例如暫停後重開、別的對話、重新驗收）或真實輸出樣本，各一列，則寫「跟改之前一樣」看得到的結果；這些列不算在 3–5 列內。實作會在暫存複本對照 main 跑這幾列，審查逐列對照有沒有做到、測到。
   - 同一段的「### 實作計畫」表（模板沒有就自己加在驗收情境之後，表頭 `| 檔案 | 改什麼 |`）：照步驟 2 讀到的程式，一列一個要改的檔，寫改什麼、為什麼；測試檔也列，專案有 `changelog.d/` 就列 `changelog.d/<slug>.md`（條目寫在片段檔，不改 CHANGELOG.md）。計畫跟規格用同一次確認，確認後 Agent 照計畫做、不再停下來交計畫，所以要寫到可以直接動手的程度。`spec-ok` 認不到填好的計畫會拒絕。
   - 卡片的 `檢查`（舊卡 `驗證`）欄是空白、`無` 或 `<…>` 佔位時，寫一條能涵蓋全部對應測試的完成檢查（目標測試＋整套；有 `suggested check:` 就以它為準），實作前它應該是紅的。欄位已有指令就不改，只在回報裡說它有沒有涵蓋這些測試。
   - 步驟 4 照推薦寫的題，Decisions 每題加一筆：`- D-nn YYYY-MM-DD <user>：預設（確認規格時可改）：<題目> → <採用的答案>（其他選項：<…>）`（`<user>` 用步驟 1 的 user，D 編號接著卡上最後一筆）。
   - 用 `card.py gate <目標> 'spec：待確認規格（AC-1～AC-n）'` 設關卡（舊卡的 rev 由腳本處理，不要手改「關卡」與「更新」兩行）。設了之後工作桌不會派實作，只能同步（同步平常收在面板的「更多動作」m 裡）。
   - History 加一行 `- YYYY-MM-DD HH:MM：/desk:card spec 產生規格草稿（AC-1～AC-n），待確認`。
6. **回報**：先跑 `card.py overlap <目標>`（實作計畫跟登錄表上其他進行中的卡同檔時，每個同檔印一行「同檔預警：…」，沒有印「同檔預警：無」）。先一句結論（寫了幾條驗收情境、計畫幾項、關卡已設），有同檔時接著把預警行原樣附上，並建議「先合哪張」或「改成疊放（`new` 時 base 指向另一張的分支）」；有預設決定時接著逐條列出（題目、採用的答案、其他選項）；再貼「## 規格」全文（含實作計畫），最後一行：
   `確認：在面板按兩次 t，或輸入 /desk:card spec <目標> ok；確認同時核准這條測試指令，之後自動派實作並自動執行它：<檢查欄全文>。確認規格同時確認上面列的預設決定；要改哪一條（含預設）直接說。`
   （`<檢查欄全文>` 要原樣印出卡片「檢查」欄的整條指令，不縮寫；使用者確認前看得到他核准的是什麼。）
   （沒有預設決定時省略「確認規格同時確認上面列的預設決定；」那句與「（含預設）」。）
   使用者要改時照使用者的話改那一列（改預設的連 Decisions 那筆一起改），關卡維持 spec，不要自己清。
