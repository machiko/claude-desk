# /desk:card

腳本是 `python3 ${CLAUDE_PLUGIN_ROOT}/skills/card/scripts/card.py`（下面寫成 `card.py`）。收到 `/desk:card <args>` 時：

- `new`、`archive` 與 `changelog`：直接執行 `card.py <args>`，把輸出原樣給使用者。
  - `new` 之後提醒：接著用 `/desk:card spec <slug>` 產生規格。`new` 不建 `changelog.d/<slug>.md`（空片段會讓發版合併報錯），條目由實作時寫。
  - `archive` 之後**不要**替使用者刪 worktree 或分支；只印出指令由使用者自己跑。
  - `changelog <版本>`：在主 repo、要發的 PR 都合併之後執行；它把 `changelog.d/*.md` 合併成 `## <版本>` 段並刪掉片段檔，沒有片段、版本段已存在、片段不是 `- ` 開頭都會報錯不改檔。之後改版號、commit、打 tag 都由使用者自己做，不要替他 commit。
- `spec <目標> ok`：執行 `card.py spec-ok <目標>`（清關卡、狀態改「規格已確認…，可派實作」、記 Decisions／History），輸出原樣給使用者。只有使用者明確說要確認時才跑，不要自己判斷規格夠好就替使用者確認。
- `done <目標> <狀態一句>`：執行 `card.py done <目標> <狀態一句>`，輸出原樣給使用者。在主對話（不派背景 Agent）改了檔案、commit、跑了測試或做了決策，告一段落時用：狀態改成那句（60 字內，沒驗證的寫「待確認」）、下一步改成「到面板按 v 執行完成檢查」、History 記日期、分支、HEAD 短 sha 與那句（有未提交的檔會註明幾個）；「等你」「關卡」「檢查」不動。規格還沒確認（關卡是 `spec：…` 或認不到填好的 AC）會拒絕。狀態只寫發生了什麼：那句含 commit（7～40 碼英數混合的 hex）、`AC-數字` 或 `D-數字` 時也會拒絕、卡片不動，這些代號寫在 History。它不會把檢查或審查標成通過，那由面板 `v` 與自動流程記錄。整段流程見 `/desk:flow`。
- `spec <目標> [需求描述]`：照下面「產生規格」做。
- 沒帶參數就印用法，不猜。

`<目標>` 可以是 worktree 資料夾名（slug）、任務名（完整或唯一部分）或 `main`（主 repo）。

設定（主 repo、worktree 位置、登錄表、模板、專案規則）在 desk 的 `dispatch.json`：全域那份疊上目前專案的 `~/.claude/handoffs/<repo>/dispatch.json`，說明見 `card.py` 開頭。要在專案的 repo 或 worktree 裡執行。

## 產生規格（spec）

規格是這件事的唯一依據：審查會逐條對照驗收情境，「沒做到」「沒測到」都算 HIGH，會被自動修正。所以每一條都要寫得能驗證。

1. **找卡**：`card.py card <目標>`，記下 path、root、format（DESK 新卡／CARD 舊卡）、branch、gate、check、spec、已填的 AC、user，以及 `rule:` 開頭的專案規則（寫規格時都要遵守）與 `suggested check:`。找不到就把腳本列出的任務給使用者選，不要猜。
2. **讀現況（唯讀）**：
   - 整張卡：狀態、下一步、Scope、Decisions、History。
   - `git -C <root> log --oneline -10`、`git -C <root> status --short`；分支已有改動就看它相對 merge-base 的 `git diff --stat`。
   - 需求牽涉的程式：路由、控制器／服務、權限設定、既有測試。範圍大就派 Explore agent 查，只帶回結論。
   - 不改程式、不 commit、不碰其他任務的卡。
3. **已有規格時**：`filled AC` 不是 none，就先用 AskUserQuestion 問「取代／只補缺漏／取消」，照答案做。
4. **釐清問題**：只問「答案會改變驗收情境」的事，能從卡片或程式讀到的不要問。
   - 用 AskUserQuestion，一次最多 4 題，總共 3–5 題；每題 2–4 個具體選項，推薦的放第一個並標「(Recommended)」。
   - 優先問：誰能用（角色與資料範圍）、邊界與錯誤時要怎樣、哪些明確不做、有沒有寫入操作、要不要相容舊資料。
   - 需求描述與卡片已經夠清楚就不問，直接寫。
5. **寫進卡片**：
   - `card.py spec-init <目標>`（沒有規格段才會插入模板的空白段）。
   - 用 Edit 改那張卡的「## 規格」：目標一句、非目標一句、驗收情境表 3–5 列。寫入前重讀卡片；跟步驟 2 讀到的不同就停下回報，不要覆寫。
   - 每一列：
     - 給定：角色、資料、前提狀態。
     - 當：操作或事件。
     - 則：看得到的結果（畫面、回應碼、資料、log），不寫實作方式。
     - 對應測試：既有的寫測試的完整名稱；還沒有的寫預計名稱並標（新）。
   - 牽涉權限、資料範圍或寫入時，至少一列寫越權或範圍外的情境。
   - 同一段的「### 實作計畫」表（模板沒有就自己加在驗收情境之後，表頭 `| 檔案 | 改什麼 |`）：照步驟 2 讀到的程式，一列一個要改的檔，寫改什麼、為什麼；測試檔也列，專案有 `changelog.d/` 就列 `changelog.d/<slug>.md`（條目寫在片段檔，不改 CHANGELOG.md）。計畫跟規格用同一次確認，確認後 Agent 照計畫做、不再停下來交計畫，所以要寫到可以直接動手的程度。`spec-ok` 認不到填好的計畫會拒絕。
   - 卡片的 `檢查`（舊卡 `驗證`）欄是空白、`無` 或 `<…>` 佔位時，寫一條能涵蓋全部對應測試的完成檢查（目標測試＋整套；有 `suggested check:` 就以它為準），實作前它應該是紅的。欄位已有指令就不改，只在回報裡說它有沒有涵蓋這些測試。
   - 用 `card.py gate <目標> 'spec：待確認規格（AC-1～AC-n）'` 設關卡（舊卡的 rev 由腳本處理，不要手改「關卡」與「更新」兩行）。設了之後工作桌不會派實作，只能同步（同步平常收在面板的「更多動作」m 裡）。
   - History 加一行 `- YYYY-MM-DD：/desk:card spec 產生規格草稿（AC-1～AC-n），待確認`。
6. **回報**：先一句結論（寫了幾條驗收情境、計畫幾項、關卡已設），再貼「## 規格」全文（含實作計畫），最後一行：
   `確認：在面板按兩次 t，或輸入 /desk:card spec <目標> ok；要改哪一條直接說。`
   使用者要改時照使用者的話改那一列，關卡維持 spec，不要自己清。
