# /desk:flow：在主對話走六段

desk 只讀卡片與 git，看不到對話內容。在主對話（不按 `g` 派背景 Agent）直接開發時，照下面六段走，並在每段告一段落時把進度寫回卡片，面板才跟得上。

收到 `/desk:flow` 時：讀這份說明，用 `python3 ${CLAUDE_PLUGIN_ROOT}/skills/card/scripts/card.py card <slug>` 看那張卡在哪一段（gate、spec、check），告訴使用者現在在哪一段、下一步做什麼；之後照這份說明做。

哪張卡：`/desk:flow <slug>` 有帶就用它。沒帶 slug 時用目前 worktree 的資料夾名（`basename "$(git rev-parse --show-toplevel)"`；slug 就是 worktree 資料夾名），在主 repo 開發時用 `main`。`card.py card` 回報找不到或不唯一時，把登錄表列出的任務名給使用者選，不要猜。

原則：

- 對話只寫卡片的「狀態」「下一步」與 History（用 `/desk:card done`），不自己把「檢查」「審查」標成通過；那由面板 `v` 與自動流程記錄。
- 背景 Agent 在同一個 worktree 跑時不要動手改（面板「現在」卡顯示 Agent 執行中）；等它做完或在面板按 `k` 停掉再改。
- 寫回指令：`/desk:card done <slug> <狀態一句>`。狀態 60 字內、沒驗證的寫「待確認」。下一步依關卡三選一：平常寫「到面板按 v 執行完成檢查」（面板第二列會說「按 v 執行完成檢查，通過後按 w 派審查」；沒有背景流程時 v 只跑檢查，不會自動接審查）；審查已過關後的新進度寫「等自動重新檢查與審查；沒動靜就到面板按 v」（開流程的對話開著面板時會自己重跑檢查與審查，其他情況照第二列按 v）；審查已過關但審查檔之後沒有新 commit（或沒有審查檔）寫「到面板照「輪到你」開 PR 或合併」（結論仍算數，面板停在合併段，不會重跑）。這幾句面板都認得，按 g 不會派「繼續」。History 記日期、分支、HEAD 短 sha 與那句（有未提交的檔會註明幾個）；「等你」「關卡」「檢查」不動。規格還沒確認會拒絕。

## 1 規格

- 對話要做什麼：`/desk:card spec <slug> [需求]` 讀卡與程式、問釐清問題，寫目標、非目標、驗收情境（AC-n）、實作計畫與完成檢查，關卡設 `spec：待確認規格`。使用者要改哪一條就改那一列，關卡維持 spec；只有使用者明確說確認時才跑 `/desk:card spec <slug> ok`。
- 面板怎麼看得到：六段停在「規格」，第二列寫「看過規格後按 t 確認」。使用者在面板按 `t` 兩次（或輸入 `/desk:card spec <slug> ok`）清掉關卡，才進實作：面板按 `t` 確認後自動派實作；在對話用指令確認的，回合結束後自動派。

## 2 實作

- 對話要做什麼：照「## 規格」的驗收情境與「### 實作計畫」在任務的 worktree 改程式；先寫測試（測試名稱照「對應測試」欄），再實作。非目標不做；規格做不到或要改，先改「## 規格」並在 Decisions 記一筆，或寫進「等你」問使用者。專案有 `changelog.d/` 時條目寫在 `changelog.d/<slug>.md`。告一段落就 `git commit`，再 `/desk:card done <slug> <狀態一句>`。
- 面板怎麼看得到：commit 與寫卡片都會讓面板馬上重讀；「現在」卡的狀態換成那句，History 多一行。沒寫回時，分支最近的 commit 比卡片新，現在卡會提示卡片落後。

## 3 檢查

- 對話要做什麼：可以先在對話跑一次卡片「檢查」欄的指令確認是綠的，但結果不算數，不要寫成「檢查通過」。請使用者到面板按 `v`。有未提交的檔先 commit，完成檢查與審查只看 commit 過的內容。
- 面板怎麼看得到：使用者按 `v` 執行完成檢查（第一次會先列出指令請他核准），動態寫「檢查通過」或「檢查未通過（exit n）」，六段的「檢查」打勾或標紅。沒過就回到實作段，在對話修好、commit、`done`，再按 `v`。

## 4 審查

- 對話要做什麼：不自己審、不自己寫審查結論。檢查通過後請使用者在面板按 `w` 兩次派審查（新對話，自己重新跑完成檢查、看 diff）。審查有 CRITICAL 或 HIGH 時，流程會自動派 Agent 依 `.task/REVIEW.md` 修正，最多兩輪；這段時間不要在同一個 worktree 改程式。使用者想在對話裡修時，先在面板按 `k` 停掉修正的 Agent，再照 `.task/REVIEW.md` 修、commit、`done`，然後按 `v` 重新檢查、`w` 重新審查。只有 MEDIUM／LOW 就過關：不影響行為的 MEDIUM（規格紀錄、文件、命名、重複這類）審查直接記錄（審查檔標「記錄、不修」、卡片 History 一行），不寫進「等你」，下一步就是開 PR；可能影響行為的才在「等你」問，選修掉的改完 commit 後六段退回檢查。審查過關後在對話裡改了又 commit，`done` 會寫「等自動重新檢查與審查；沒動靜就到面板按 v」：這個對話開的流程會自己重跑，別的對話開的（或沒動靜）要按 `v`；還沒 commit 就 `done`，寫的是「到面板照「輪到你」開 PR 或合併」，要重跑得先 commit。
- 面板怎麼看得到：關卡變成 `review：CRITICAL n、HIGH n、MEDIUM n、LOW n；結論`，`e` 開審查檔；過關後六段走到「合併」。審查之後又有 commit，那次審查不算數，六段退回「檢查」。

## 5 合併

- 對話要做什麼：使用者要求時 `git push -u origin <分支>` 並對基準分支開 PR（GitHub 用 `gh pr create`）；PR 網址與分支頂端 commit 用 `done` 或手動寫進 History。不 force push、不推別的分支、不合併 PR。
- 面板怎麼看得到：面板唯讀 PR 與 CI（GitHub 用 `gh`、Bitbucket 用 MCP），第二列依序寫「push 分支並開 PR」「PR 的 CI 在跑」「合併 PR（p 開啟）」。PR 開著又有新 commit 時出現「⇡ push」。合併由使用者按，合併後六段走到「上線」。

## 6 上線

- 對話要做什麼：不打 tag、不部署。要上線的卡由使用者把關卡寫成 `release：…`（或請對話用 `/desk:card gate <slug> 'release：…'`）；打 tag 與部署由使用者的流程做，卡片「部署步驟」可以在對話裡補。
- 面板怎麼看得到：commit 進了 `v*` tag、關卡是 `release：…` 時出現 `u 上線確認`；使用者按 `u` 兩次清掉關卡並記 History，六段走完。

## 歸檔

- 對話要做什麼：上線確認後 `/desk:card archive <slug>`（卡、審查檔與 `.task` 的計畫／報告複製到歸檔資料夾、登錄表移到已歸檔段）；不替使用者刪 worktree 或分支，只印出指令。
- 面板怎麼看得到：也可以在面板點兩次「⌫ 歸檔」；歸檔後那張卡從任務清單消失。

## 建議貼進專案 CLAUDE.md 的規則

一行就好，流程細節留在這份 skill，需要時用 `/desk:flow` 載入：

```
- 改了檔案、commit、跑了測試或做了決策的對話，告一段落時跑 `/desk:card done <slug> <狀態一句>` 寫回卡片（流程見 `/desk:flow`）。
```
