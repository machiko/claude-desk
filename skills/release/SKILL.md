# /desk:release：發版

收到 `/desk:release …` 時照這份做。參數是面板列好的這次要發的卡，不用再查哪些卡已合併待發版；卡片位置用 `python3 ${CLAUDE_PLUGIN_ROOT}/skills/card/scripts/card.py card <slug 或卡名>` 查。

## 參數

例：`/desk:release 「Beta」PR #12、「Gamma」PR #13（歸檔並移除 worktree 與分支：beta feature/b；「Gamma」有 release 關卡，部署後按 u；已在面板確認：版號照慣例直接做）`

- 括號前：這次要發的卡，`「卡名」` 後面接 PR 編號（沒有 PR 的只有卡名），用「、」分隔。只發這幾張，登錄表上其他的卡不列、不改。
- 括號裡 `歸檔並移除 worktree 與分支：` 後面：發版後要清理的卡（都已合併、沒有 `release：` 關卡），每張是「slug 分支」，用「、」分隔。
- 括號裡 `「卡名」有 release 關卡，部署後按 u`：這張不在這次清理。`都有 release 關卡，不清理，部署後按 u`：這次沒有要清理的卡。
- 括號最後的 `已在面板確認：版號照慣例直接做`（確認段）：使用者已在面板按兩次 z 確認、同意照慣例版號，照下面「確認方式」第一條做。只有確認段時括號裡只有它。
- 沒有括號：舊版請求或手打的，照上面的意思自己判斷，不確定就寫進題目讓使用者選。

## 確認方式

請求有沒有確認段，分兩條路：

- 有確認段：不寫題目，版號照慣例提（第 2 點）。先在每張卡的 Decisions 記一筆「D-nn <日期> <user>：發版 v<版號>（<理由>），面板確認」，「狀態」寫「發版 v<版號>：進行中（<步驟>）」，再照第 3 點的順序做完、中間不再問；「等你」不動。請求裡另寫了版號（例如在確認段旁加「用 v1.0.0」）就用那個版號、不照慣例改提，照樣不出題，Decisions 的理由寫「使用者指定」。判斷不了版號（沒有 v* tag、兩個候選都合理）才寫題目停下：照第 1 點的範本寫題、不打 tag，等使用者回答。
- 沒有確認段（手打的）：照第 1 點的範本寫題目、寫完就停（第 4 點）。

1. 在這幾張卡的「等你」寫同一題，照這個範本、整題不用「；」（面板才會當成一個決策）：

   `發版 v<版號>（<卡名與 PR，例如「Beta」PR #12>，<版號理由>），照做會依序：<動作，用 → 串>：A) 照做 v<版號>（推薦） B) 改用 v<另一個版號> 照做 C) 先不發`

2. 版號照這個專案過去的慣例提，寫出理由。
3. 照做的動作依序是 整版審查 → 合併 CHANGELOG 片段 → 改版號 → 跑完整檢查 → commit → 打 tag → push 主分支與 tag → 等 CI 通過；參數有要清理的卡時最後多一項「歸檔並移除 worktree 與分支」。照專案文件的發版步驟補上專案自己的步驟與收尾（desk 自己是 `docs/WORKFLOW.md` 的發版段），題目照實際要做的順序列。
4. 寫完題就停，等使用者在面板按 a／b／c 再按 `f` 送回「「任務名」決策：…」。
5. 有確認段照做時，失敗處理與清理同下面「收到決策」「清理」：任何一步失敗就停在那步、「狀態」寫原因。

## 整版審查

每張卡只審查一次（修完只跑測試、不複審），卡片之間會不會互相打架留到這裡看。合併 CHANGELOG 片段之前做，有確認段也照做：

- 範圍：上一個 `v*` tag 到 `origin/main`（先 `git fetch`）：`git diff <上一個 v* tag>..origin/main`。沒有 `v*` tag 就照「判斷不了版號」寫題目停下。
- 派一個審查 Agent 做（新對話、不接續任何實作的 Agent），對話不自己邊看邊修：照 `${CLAUDE_PLUGIN_ROOT}/templates/review.md` 的「整版審查」段，重點是同一個檔被多張卡改、一張卡改了另一張依賴的行為；各卡自己的規格不重審，分級照舊。
- 結果寫進 reviews 資料夾的 `release-v<版號>.md`（登錄表旁邊的 `reviews/`，跟各卡審查的留檔同一處；沒有專案資料夾時是 `~/.claude/handoffs/reviews/`），開頭一行 `整版審查：CRITICAL n、HIGH n、MEDIUM n、LOW n`。
- 有 CRITICAL 或 HIGH：停在這步、不合併 CHANGELOG、不打 tag。「狀態」寫「發版 v<版號>：整版審查擋下」，這次每張卡的「等你」寫同一題（有確認段也寫）：`整版審查 CRITICAL n、HIGH n：A) 開修正卡再發 B) 照發 C) 先不發`。選 B 從合併 CHANGELOG 片段接著做；選 A、C 不發。
- 只有 MEDIUM／LOW：照常接著做，最後回報時列出這幾條與 `release-v<版號>.md` 的路徑。

## 收到決策

- 回答任一張就算數，收到決策先把每張的「等你」清成無。
- 選 A 或 B 後照順序做完、中間不再問，「狀態」寫做到哪一步。
- 任何一步失敗就停、後面的不做（還沒 push 就不 push，已 push 的不回退、不 force push），失敗的步驟與原因寫進「狀態」，要使用者決定的才寫進「等你」。
- 選 C 就清掉「等你」、什麼都不做。
- 整版審查那題不一樣：選 B 照發，從合併 CHANGELOG 片段接著做完；選 A（開修正卡再發）或 C 就清掉「等你」、不發，A 由使用者另外開修正卡。

## 清理

- 歸檔並移除 worktree 與分支：CI 通過、各卡狀態寫好之後才在主 repo 跑 `/desk:card archive <slug>… --cleanup`（參數列的 slug 一次給），把沒移除的項目與原因告訴使用者；保留的項目不要自己加 `--force`／`-D` 去刪。
- 有 `release：` 關卡的卡留給使用者部署後按 u（確認上線時自動歸檔），不帶 `--cleanup`。

## 不做的事

- 題目沒列的事一律不做（force push、改寫歷史、合併 PR、刪分支、改清單外的卡），要做就另外問；有確認段時「題目沒列的事」以「確認方式」第 3 點的動作順序為準。
- 面板與背景 Agent 都不打 tag；只有使用者在題目選了照做，或請求帶確認段，對話才打 tag 與 push。
