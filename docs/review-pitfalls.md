# claude-desk 審查常犯錯誤清單

> 每次審查先讀這份，逐條對照改動。回顧或審查發現過去出現過的問題時追加於檔尾，既有條目不改。

## 追加
- 規格：實作跟「### 實作計畫」寫的做法有出入（連正規式多錨一個 `$`、改成每次注入這類小差異都算）就在 History 寫明改了什麼、為什麼，不要寫「無偏離」；需求中途改了先改「## 規格」並在 Decisions 記一筆
- 測試：改 README、docs/WORKFLOW.md 或 skills/*/SKILL.md 的字句前，先 grep skills/card/tests 與 scripts/tests 有沒有斷言那段文字的 Python 測試一起改，並跑 `python3 -m unittest discover -s skills/card/tests`（CI 會跑，`claude plugin test` 不含）；AC 的測試放在 Python 那邊時，卡片「檢查」欄也要串上它
- 重複：規則搬到一處（例如某份 skill）後，README 指令表、WORKFLOW 等其他地方只寫用途並連過去，不要再寫摘要版的規則
- 註解：改了測試斷言或程式行為，同一支的 docstring／註解（AC 編號、步驟數、函式說明的位置）一起對照改；沿用別張卡的測試時，AC 編號要標是哪張卡的
- 邏輯：從登錄表挑「第一張」符合條件的卡當依據時，想一下新、舊兩張同時符合（例如上一版沒歸檔的「已發版」卡）會不會擋住或蓋掉新的；要最新的就照版號或時間挑，記下的狀態不要倒退
- 並行：重新整理很慢（claude agents、git／PR 探測、派工），要讀的檔案（卡片 worktree 裡的檔）可能在這輪跑到一半就被同回合的指令（archive --cleanup）刪掉；判斷用的資料在組快照時一起讀，不要排在重新整理尾端
- 文件：新增一個步驟或動作時，grep 文件裡「最後一項」「第 n 步之後」這類講順序的句子一起改，不要只加新段落
- 風格：Python 測試在類別中間插入方法時，對照前後空行（方法之間一行、類別之間兩行）
- 文字：改了或新增面板上看得到的提示句（檢查列、輪到你、toast）時，逐一對照會出現這句的每個情境（例如「從沒核准」與「改過」）字面是否都成立，同一件事在各處的說法要一致
- 命名：行為改了，測試名與函式名裡描述舊行為的字（asks、dialog、取消）一起改；名字是別張卡驗收情境的對應測試時，連那張卡的對照一起改，或在 History 記不改的原因
- 跨對話：$.store 是所有開著 desk 的對話共用的，回合結束要處理的待辦記下是哪個對話記的（或放對話自己的 $.state），只處理自己的，store 只記已處理過的版號，別的對話的回合結束才不會拿走它
- 版面：讓某一列變寬（多幾欄）時，對照摘要列與面板「由寬到窄試」的各版，算出改走窄版的新寬度；測試因此放不下時不要只把測試寬度調大，要在規格或 Decisions 寫明從幾欄起改走窄版、哪些字會被截
- 測試：規格寫了邊界（例如寬度 < 30 的窄畫面），就要有一支測試真的把 fixture 調到那個條件；整套測試現有的 fixture 到不了的邊界等於沒驗，寫 AC 時先確認 fixture 到得了
- 規格：修正輪實際做法跟 Decisions 寫的不同（例如截短的是左邊那句而不是提醒）時，回頭改 Decisions 或補一筆，不要只留在 History
- 邊界：往卡片或模板插一行時，新行自己帶換行，不要假設插入點後面剛好有空行（自訂模板「## 規格」下可能直接接「- 目標：」）；測試要有一支用沒空行的 fixture
- 提示：新增一種卡片狀態（例如開卡就預填驗收情境、設 spec 關卡）時，對照面板依同樣條件（認得到 AC、關卡種類）給的「輪到你」與六段註記，確認在新狀態下講的下一步做得到
- 測試：要測「模板長這樣時」的情境，直接寫一份最小的 fixture 模板，不要用 re.sub 去改內建模板；模板寫法一變 sub 就不命中，測試變成在跑原本的模板、永遠綠
- 資料：要加 `--force` 繞過 git 的拒絕（例如含 submodule 的 worktree）前，自己的「乾淨」檢查要補上 git 原本在擋的東西：submodule 裡的未提交改動（`--ignore-submodules=none`）、被忽略的本機設定、沒推上遠端的 commit；測試每種各放一個真的會被刪的檔或 commit
- 相容：依 git 或其他 CLI 的錯誤訊息字面判斷時，執行時設 `LC_ALL=C`（或改看結束碼、porcelain 輸出），非英文 locale 的翻譯訊息才比對得到
- 重複：把一組條件抽成共用常數（例如 NEEDS_YOU）後，grep 原本手寫同一組條件的地方全部換掉，否則「避免兩份」沒達成，之後改一邊漏一邊
- 命名：改動讓既有變數的意思變了（narrow 從「太窄」變成「一串版」）時順手改名，別讓舊名字帶著新意思，後面的條件會被看錯
- 通知：同一件事可能從兩條路徑觸發（例如派工隊伍先停下流程，同一輪重新整理的另一段拿舊快照又停一次）時，寫動態、toast、系統通知前先確認這次真的改了狀態（看存檔函式回傳有沒有改），不要無條件發；各路徑的原因句用同一個常數或函式參數產生
- 流程：新增一種讓流程停下的原因時，照提示把「重開」走一次：按下去派的是什麼、會不會開新的一輪而丟掉輪數／recheck／資安審查這些狀態、重開後會不會重做已經做過的步驟
- 可維護性：要給別的模組判斷的狀態記成結構化欄位，不要把顯示用的原因句存起來，再用開頭、結尾或標點切字串認回來
- 派工：手動動作（g、/desk go）要接續自動流程時，不要直接拿自動流程的 `dispatch(..., { auto: true })`：auto 會跳過手動派工的拒絕檢查（Agent 在跑、已合併、規格擋著），排隊時被當成自動項目（被額度煞車丟掉、別的對話的流程被拒），流程擁有者也不會改成這個對話；要嘛補做這些檢查並接手，要嘛另給一個旗標
- 測試：「同一件事只寫一筆」這類去重的斷言，要先確認測試裡第二次真的會再走到那條路徑（派工已標成處理過就不會再呼叫寫入）；突變拿掉去重後測試仍全綠就等於沒驗到，要補一支讓同一件第二次放棄的測試
- 註解：重試迴圈的常數名與註解要寫明是「含第一次的總次數」還是「重套次數」，並跟使用者看到的動態句數字一致（MAX_SAVE_RETRIES 寫「重套最多 3 次」，實際是含第一次共寫 3 次）
- 解析：把「只認開頭」的比對放寬成任何一行（正規式加 /m、改成 append 接在草稿後）時，想一下同一段有兩筆符合（同一件重填、兩件接在一起）要回傳哪一筆或全部，各寫一支測試；fixture 的讀取要反映前一次寫入（prompt.read 讀得到 fill 填進去的字），重填的情境才測得到
- 文字：把某件事的按鍵說法改掉（例如「按 ⇡ 開 PR」改成「按兩次 n」）時，同一件事的動態、toast、通知與「輪到你」要一起改；先 grep 舊說法，不只改面板第二列
- 註解：行為改了（例如按鈕加了快捷鍵）就 grep 舊說法，連型別與介面的註解一起改（PaneActions 的 archive、release 仍寫「沒有快捷鍵」）
- 提示：改了某顆鍵出現在 footer 的條件（收進 m、處理中過濾、只在某段列）時，grep 面板其他列、動態、toast 裡叫你「按 X」的句子，逐一確認那些情境下 X 還畫在 footer 上；不在就讓那句跟著同一個集合判斷（照 heldReason 的做法），不要只守「▶ 輪到你」
- 狀態：新增一個記在這個對話的暫時狀態（atom、鎖、hold）而且會改「輪到你」時，列出它該失效的每條路徑（別的對話派工或接手流程、Agent 已在跑、卡片改成等你、/clear 開新對話），清不到的就讓它排在即時狀態（Agent 執行中、等你、等回覆、等批准）之後，不要只在自己這條派工路徑清掉；補一支「別的對話派出後」的測試
- 規格：提示叫使用者在送出前手改一段文字（例如「要改版號就改這行」）時，讀那段文字的 skill 或解析端要寫明改過的內容怎麼處理（照用、或改成出題），並有測試鎖住；不然對話會照預設做出使用者沒要的事
- 測試：測 toast／提示要走到程式真正跳出它的那一行，不要只比對常數字面；狀態難在 fixture 造出來時，把判斷抽成回傳句子的純函式，餵那個狀態斷言整句，跳 toast 的那行只負責呼叫它
- 範圍：規格目標或 Decisions 標「待補文件：」的說明是留給發版「補文件」那步一次補的，功能卡實作時不要先改 README／WORKFLOW 的功能說明段（實作計畫沒列的檔也不改）；真的先補了，在 Decisions 記一筆並註明發版時這張略過，免得發版重補
- 文字：有條件地省略一句話時，同一行裡依附那句的字（例如「（含預設）」）也要一起省略；逐個情境把省略後的整行唸一遍，確認字面都成立
- 風格：改寫說明句時不在括號裡再套一層括號，也不要順手換掉原本的分隔符號（「，」「、」「；」照原句）
- 契約：改了卡片或檔案的寫入格式（例如 History 行加上時間、改某句固定文字）時，grep 專案裡讀這個格式的正規式與模仿腳本效果的測試替身（例如 hooks/touch.ts 的 SPEC_OK_HISTORY、tests 裡的 confirmCard），讀寫兩端一起改；測試替身要寫跟真腳本一樣的新格式，再補一支新格式的斷言，不然整套照舊格式跑永遠綠
- 死碼：拿掉某條路徑上唯一的呼叫（例如不再讀審查檔算 MEDIUM）時，grep 被呼叫的函式、型別欄位還有沒有別的程式在用；只剩自己的測試在用就連測試一起刪，不要留著讓測試驗證沒人用的程式
- 派工：把「沒派成就留著下次再派」加到自動派工或外部呼叫上時，想一下一直失敗會不會每次重新整理都重來（回傳「有動作」會 2 秒後再整理、每次都跳 toast），以及「回傳失敗但 Agent 其實已啟動」（agents 清單還沒列出）會不會再派一個；自動只試一次或退避，沒派成就停下並寫明怎麼重來，補「一直失敗」與「已啟動未列出」各一支測試
- 流程：審查提示或契約叫「等你」保留某題時，對照「這份審查有 CRITICAL／HIGH、會自動派修正」的情境：修正 Agent 結束時「等你」有內容，askedOnCardAtEnd 會當成它問的，流程停住、不跑檢查與複審；有 CRITICAL／HIGH 時題目留在審查檔、等你留無，過關那次再合成一題問
- 派工：要判斷「這次流程做過某一步」（例如跑過資安審查）時，看流程紀錄裡那一步的結構化欄位（例如 securityHead），不要看 jobs.last 是哪一種派工；過關後推送、開 PR、同步也會覆寫 last，中間插一次就判斷錯
- 一致性：同一個數字或判斷在兩處算（例如存進去的總執行與畫面上的總執行、自動流程與「輪到你」）時，共用同一個函式，或把封頂、例外條件一起帶過去；改了一邊的條件就 grep 另一邊，補一支「兩邊結果相同」的測試
- 型別：同一個物件形狀（例如時段 `{ from; until }`）在兩處以上寫成行內型別時，抽成具名型別；兩個欄位一定一起出現時（runFrom／runUntil），合成一個可選的物件，不要拆成兩個各自可選的欄位再用 `?? Infinity` 補；能從前面的檢查得知的值（`c.pr` 一定有）就收那個值，不要用 `!`、`as any` 跳過型別檢查
- 流程：新增一個排在 autoChain 主判斷之前的自動派工（例如回答 B 派修正）時，條件要加「最後一次派工已處理（last.handled）或流程已過關」：高風險卡資安審查在跑時「等你」照樣能答，搶先派工會覆寫 jobs.last，剛結束的那次不歸檔、結論沒處理（HIGH 不修、關卡被改回 無）；補一支「前一次派工剛結束、還沒處理時觸發」的測試
- 命名：欄位或參數的意思變了（例如 round 從「這輪流程第幾輪」變成「整張卡累計第幾輪」）就改名或另開欄位，不要沿用舊名只靠註解說明；測試的 docstring 也照新意思改
- 規格：實作把文字、顯示位置或關卡寫法改得跟驗收情境不同（例如「已修正・未複審」改寫在合併段）時，在「等你」問「照 AC 做或改規格」，選了改規格就把 AC 那列一起改；不要只寫在 History，審查會判成 AC 沒做到
- 註解：改了選項的字母或順序（例如「修掉」從 B 移到 C），要 grep 所有寫死「回答 B」「選 B」的註解、提示句與測試 docstring 一起改；判斷邏輯看選項文字不看字母，不代表說明文字也不用改
- 一致性：改了派工規則（例如自我檢查只拿掉一處、只跑對應測試）時，同一件事在寫規格的說明、WORKFLOW、flow SKILL 的描述要在同一個 PR 改掉，不要留舊說法
- 流程：疊在別張卡分支上的後續卡，工作桌的審查 diff 與開 PR 目標仍是 main；原卡還沒合併時不要確認後續卡的規格，等原卡合併後再派，否則會把原卡改動重審一遍、PR 也帶著原卡的 commit
- 提示：改了會組進多種派工的共用規則（例如 testRule 改成收尾不跑整套）時，grep 跟它接在同一份提示的開頭句（解衝突步驟、額度接續、修正輪的「修到完成檢查綠」），逐種派工把整份提示唸一遍，不要留兩句指示相反
- 命名：新增欄位或參數前 grep 同名的既有欄位與變數（例如 base 已是複審起點 commit、merge-base 分叉點），同一個詞不要在相鄰模組代表兩件事，改用帶種類的名字（baseBranch）
- 文件：改了既有設定或指令的預設行為（例如 card.base 從 new 的預設基準變成只在 detached HEAD 時用）時，changelog 片段用「調整」寫出舊設定的意思怎麼變，不要只寫新增的功能
- 測試：同一個功能有好幾條觸發路徑（Edit／Write／Bash、實作／回覆／修正）時，每條各要一支「該有反應就真的有反應」的正向測試，只斷言「沒提示」的測試在那條路徑整個拿掉時照樣綠；斷言「沒反應」時，確認擋下它的是要測的那個條件，不是同一支測試前面已經設好的前提（模板已換成沒有那一段、find 回 -1）；寫完在暫存複本拿掉那個分支跑一次，確認會紅
- 相容：拿目前版本的模板或格式去比對、解析既有的卡時，先想 desk 升級前開的舊卡（模板改過幾行）會怎樣：會不會每次寫入都被判成錯、被要求照新版改；規格要寫明舊卡怎麼處理（照開卡時的版本比、只提示一次或略過），並用一張舊模板開的卡測一次
- 路徑：從 Bash 指令字串認出檔案（例如卡片路徑）時，列出同一個檔的各種寫法（絕對路徑、相對路徑 `.desk/CARD.md`、`./`、`~/`、加引號）逐一決定認不認，不認的寫進規格或 History；認的寫法各補一支測試
- 文件：規格中途改了（Decisions 改了 AC）之後，changelog 片段與檔頭註解照改過的 AC 重唸一遍，不要留改之前的說法（例如「背景 Agent 寫壞也記動態」）
- 風格：測試要在工具呼叫前先設好替身狀態（例如 bash.writes）時另起一行設定，不要用逗號運算式塞進 await 或陣列元素（`await (x = …, $.tool.call(…))`），副作用的先後要停下來看才懂
- 一致性：在派工提示或模板加新規則句時，grep 同一份提示、模板裡說相反的舊句一起改，不要讓兩句指示並存（例如「細節寫在歷程」跟新範本「歷程不寫檔名」）
- 剝控制碼：去控制碼或雜訊的正規式（例如補半截顏色碼的 `^[\d;]*m`、跳欄換空白）要拿一般文字跑一次（`m` 開頭的英文字、句中出現同樣關鍵字的問句），確認不會吃掉或拆斷正常內容；只認殘留碼時要求前面至少有一個數字或分號，共用範例也放一筆這種正常文字
- 規格：改修正提示的規則（加句、拿掉清單）時，修正有兩條派出路徑：自動修正輪（fixHead、帶 FixReason）與按 g 的修正（manualFixHead、不帶 fix，含 MEDIUM_FIX_NOT_SENT 重派），判斷「這次是修正」要兩條都認得，測試各列一種；Agent 被停止後重開是接著實作，不算修正
- 規格：「比改之前短」「≤ 300 行」「沒改既有測試」這類只對這次改動成立的驗收情境，不要寫成寫死數字的永久測試（之後改到共用提示或檔案的分支都會紅）；規格寫成審查用 main 對照核對一次、結果記在歷程
- 死碼：把函式包一層或改走別的入口（例如 manualFixHead 改走 manualFix）之後，grep 舊函式還有沒有正式程式碼在呼叫；只剩測試在用就連測試一起收掉，不要留著讓測試驗證沒人用的程式
- 測試：功能在正式流程裡走的是帶旗標的版本（例如發版跑 `archive … --cleanup`）時，至少一支測試帶那個旗標跑，鎖住「清理前先讀資料」這類順序約束；只測不帶旗標的版本，順序寫反照樣綠
- 一致性：同一個資料夾或設定路徑在 TS 與 Python 兩邊都要用時，不要各自用預設值去算（審查留檔位置，hooks 看 reviewsDir、card.py 固定找登錄表旁）；由一邊算好寫進共用檔給另一邊讀，或兩邊讀同一個設定並補一支設了自訂值的測試
- 派工：新增一條自動派 Claude Agent 的路徑（例如外部驗收失敗後改派、排在主判斷前的派工）時，派之前跟主判斷一樣算 quotaHold，有的話停下並記 resume；dispatch 本身只在排進隊伍時看額度，直接派會繞過煞車；補一支「額度低於門檻時走這條」的測試
- 狀態：依最後一次派工改寫或藏掉面板上的 Agent（例如外部驗收時藏掉 blocked 的信標）時，條件要限定在那次派工還沒處理完、信標是那次寫的；只看 last 的種類，會連之後別處派的 Agent、還在跑卻停下等批准的 Agent 一起藏掉，面板就變成「待辦」
- 競態：用兩個來源判斷「結束了沒」時（先讀狀態檔，再看行程在不在），要先看行程、行程不在了再重讀狀態檔；順序反過來，對方剛好在兩步之間寫好 done 並結束，就會被誤判成沒回報就結束
- 統計：新增一種不在 claude agents 清單裡的 Agent（例如看信標的外部 Agent）時，對照總執行、seenAt 這類靠清單找啟動名的統計，在規格寫明它的時間算不算；要算就用它自己的在跑訊號（信標 working、行程還在）記，補一支跑超過 grace 的測試
- 狀態：拿流程紀錄的暫停原因（chain.stopped）判斷剛離開「在跑」的 Agent 怎麼結束、要寫什麼字時，想一下這個原因在按 g 重開前一直留著，中間手動派的同步、推送、回覆不會清掉它；以那次派工自己的結束方式（ended.how、這一輪清單）為準，暫停原因只在結束方式不明時補，並補一支「停掉後手動派同步、正常做完」的測試
- 提示：新增「自動派工沒派出、按 g 重派」這類停下原因時，按 g 派出的提示要跟沒派出的那次依同一份審查檔（剛結束的是資安審查就寫 SECURITY.md）；停下時把這件記成流程紀錄的結構化欄位（照 MEDIUM_FIX_NOT_SENT 的 mediumFixSecurity），不要在 manualFix 寫死 REVIEW.md，並補一支「資安審查 HIGH 後沒派出、按 g」的測試
- 重複：新寫一個做某件事的函式（例如停下這個對話的流程）前，先 grep 同一個模組附近有沒有做同一件事的既有函式（pauseOwnChain），直接用或匯出共用，不要在相鄰模組各寫一份同樣的閉包
- 狀態：新增去重、快取這類「記得報過什麼」的紀錄時，找出它描述的東西（動態、畫面、問題列）在哪些地方被清掉（教學開始／結束、/desk off、重新載入），在同一個清除點一起清；不然描述物清掉後紀錄還在，同一件事再也不報。補一支「清除點前後各跑一次」的測試
- 規格：實作時才決定的行為（規格沒寫到的邊界，例如較新格式的登錄表 card.py 照常讀寫、不提示）要在同一個 commit 寫進卡片 Decisions 或規格的驗收情境，不要只存在程式裡；審查看到規格沒寫的行為就列出來，問它是不是刻意的
- 文件：寫給外部使用者的限制要明寫門檻值與意思（「最低需要 Claude Code 2.1.302，比它舊會在面板提示」），不要只寫「以 2.1.302 開發與測試」讓人自己猜；程式、CI 與文件稱同一個值時用同一個說法
